Deep dive: what happens if a chunk crashes mid-upload?

your question

Following the real code path in apps/web/src/lib/upload.ts and apps/api/src/routes/upload.ts. Short version: the checksum is not what resumes an upload - it is a whole-file integrity/dedup hash. Resume is driven by the multipart uploadId as an idempotency key.

Failure sequence (as coded today)
  • Chunks upload in batches of 3 via Promise.all(batch), each PUT straight to S3.
  • One chunk's PUT rejects. Promise.all rejects the whole batch, so uploadFile() throws and the loop stops.
  • Chunks already PUT survive as parts inside the open S3 multipart session, but the client's in-memory parts[] array is lost.
  • On retry, the intended design: call GET /upload/status/:uploadId, get completed part numbers + eTags, skip them, resume from the first gap.
The checksum's actual role

A single SHA-256 over the whole file, computed before upload and stored in files.checksum. It does two things - neither is per-chunk resume:

  • Dedup: the sync client compares it to the last known checksum and skips re-upload when only metadata changed.
  • Integrity: proves the assembled object matches what the client intended to send.

Resume is keyed on uploadId + part numbers, not the checksum. S3 itself verifies each part via its per-part ETag on CompleteMultipartUpload.

⚠ Honest gap: resume is scaffolded, not fully wired

The uploads.uploaded_chunks column is read by the client but never written after it is initialized to [] - so GET /upload/status always returns empty. Worse, the client calls /upload/init fresh on every attempt, minting a new uploadId and a new S3 session. As written, a crash mid-upload means the next attempt restarts from scratch and orphans the previous multipart parts.

To make it real, two pieces are missing: (1) persist each completed part's eTag into uploaded_chunks after every chunk (or query S3 ListParts on resume), and (2) look up an existing in-progress upload row for the file+checksum and reuse its uploadId instead of re-initing.

How the NFRs are addressed

the ask

The design spec names five non-functional requirements. Each maps to concrete, verifiable implementation choices in the codebase - shown below with the exact mechanism and where it lives.

1 · High availability

availability > consistency
Mechanism

Graceful degradation over hard failure. Sync never goes dark: if SSE drops, the client silently falls back to 30s polling and keeps retrying SSE.

Design choices
  • API off the data path → S3 outages don't take down metadata ops
  • Best-effort SSE: a dead client stream is pruned, never blocks others
  • S3 delete failure is logged but DB stays consistent
Where
  • apps/sync/src/index.ts
  • apps/api/src/routes/sync.ts
  • apps/api/src/routes/files.ts

2 · Large file support

up to 50 GB
Mechanism

S3 multipart upload. Client slices the file into 10MB Blob chunks and PUTs each directly to storage via presigned URLs.

Why it scales
  • API never buffers file bytes - constant ~200B/request
  • Chunks upload in parallel for throughput
  • No server memory pressure regardless of size
Where
  • apps/web/src/lib/chunker.ts
  • apps/web/src/lib/upload.ts
  • apps/api/src/storage.ts

3 · Reliability

recoverable & consistent
Mechanism

SHA-256 integrity + transactional writes, with a resumable-upload scaffold (idempotency key + status endpoint). See the "Honest gap" note in Core flows - resume is designed but not yet fully wired.

Design choices
  • Idempotency key: uploads table tracks completed chunks
  • Transactional outbox: DB commit before SSE/S3 side effects
  • Checksum detects corruption & prevents redundant writes
  • Trash = soft delete; 30-day window before purge
Where
  • apps/api/migrations/003_*.sql
  • apps/api/src/routes/files.ts
  • apps/api/src/purge.ts

4 · Low latency

fast up · down · sync
Mechanism

Cut the middleman everywhere. Direct-to-S3 transfer, CDN edge downloads, SSE push, and indexed queries.

Design choices
  • Parallel chunk upload; presigned download from CDN edge
  • SSE push = near-instant cross-device notification
  • Postgres GIN FTS + indexes for search & sync_log
Where
  • apps/api/src/routes/sync.ts
  • apps/api/migrations/009_*.sql
  • storage.ts (presignDownload)

5 · Cost-effective

lazy CDN
Mechanism

Cache on access, not proactively. CloudFront caches a file only when it's first requested - no cost for cold objects.

Design choices
  • No egress through the API (S3 handles bytes)
  • Dedup skips redundant uploads & storage
  • Single shared connection pool + S3 client (Singleton)
Where
  • design spec §8 (CDN lazy)
  • apps/api/src/db.ts
  • apps/api/src/storage.ts
Honest note: CloudFront lazy caching and the 50GB ceiling are design-level decisions (prod uses S3 + CloudFront; local dev uses MinIO). The availability & reliability mechanisms - resumable upload, polling fallback, transactional outbox, soft-delete - are implemented and tested in the codebase.
